# R22: Windows OS-message dispatch, tested at last — and the three build fixes it took to get there

Closes **R22** in `OPEN-RISKS-20260813.md`, the last open item there apart from R25, which is a
deliberate trade rather than a defect. The full account, including the probes and the mutation
table, lives in that document's R22 entry; this file records what changed and why, in the order it
had to happen.

Verified on **Windows 11, `win64-msvc`, debug, AddressSanitizer on**: `.\waf.bat build` clean at
default parallelism, and the suite at **184 tests, 183 passed, 1 skipped, 0 failures**, in
declaration order and under `--gtest_shuffle`. It was 178 before. Each of the six new tests was
verified against a deliberately broken build, and each is killed by a different mutation.

**Not re-measured on Linux.** No Linux toolchain was reachable from this session. The changes that
touch shared files are a `#if defined( _WIN32 )` test file and one call swapped to an existing
cross-platform helper; nothing else leaves Windows.

---

## First, the build had to work at all

None of this is R22. All of it blocked R22, because "the suite passes on Windows" is what everything
else here rests on.

**`asm volatile` in `test_QtLikeSignal_Regression.cpp`.** GCC inline-asm syntax that MSVC does not
parse, and the only thing in the tree that stopped a Windows build outright. It is an optimiser
barrier keeping a construct/destroy benchmark from being deleted. `PerfHarness::keep()` already
existed for exactly that, with an `_MSC_VER` arm beside the GCC one, so the line now goes through it
rather than keeping a second and less portable copy of the same idea.

**`QtMimic-test` never linked `user32`.** `src/tests/wscript` had linked it since the beginning;
`external/QtMimic/wscript` never had. The result was nine unresolved externals, every one of them a
Win32 call in `EventDispatcherWin32.cpp` — the target that most needed the library was the one not
linking it.

**Every Windows binary died at startup with `0xC0000135`, silently.** ASan is on by default on
Windows here, and Windows resolves a DLL from the executable's own directory before it consults
`PATH`, which nothing puts the MSVC bin directory on. The suite did not crash; it could not start,
which looks identical from the outside. `add_AddressSanitizer_on_Windows()` now copies
`clang_rt.asan_dynamic-*.dll` next to every program it builds, so an ASan build runs as built. The
copy is deduplicated per output directory, because `src/tests/` builds two programs into one
directory and two tasks writing one output is an error in waf rather than a redundant copy.

**One failure was left alone on purpose.** A parallel build once failed with
`C1041: cannot open program database vc140.pdb` on two files. `/FS` is already set for both modes,
and the failure has not reproduced across two full clean parallel rebuilds since. Adding a second
PDB mechanism to fix something that reproduces zero times out of two is precisely the mistake R29
exists in the risk register to remember, so it is a note rather than a change.

## What R22 actually turned out to be

Smaller than filed, and in a different place.

`CoreApplication` and `Thread` construct `EventDispatcherWin32` unconditionally on Windows, so the
first native run of the *existing* suite had already put several hundred passes through the
constructor, the destructor, the `MsgWaitForMultipleObjectsEx` wait, the `wakeWaiter()` post, the
`mWakePending` collapse and the `PeekMessage` drain. That code was unobserved, not untested.

What had never executed was the handling of a message the dispatcher did not send itself:
`TranslateMessage`, `DispatchMessageA`, and the `WM_QUIT` branch. That is what the new tests cover,
in `src/tests/QtLikeSignal-test-eventdispatcher-win32.cpp`.

## The one code change: a comment that named the wrong pass

`processPlatformEvents()` runs from `processEvents()` *after* both of that function's interrupt
checks and after the event batch has been taken. So the `interrupt()` raised by the `WM_QUIT` branch
cannot affect the pass that saw the message — but the comment on that branch said it could
("interrupt() ends the current pass").

Probed rather than argued. The pass that sees `WM_QUIT` dispatches its whole batch and reports
success; the pass *after* it returns false having done nothing, deferring by one pass any work
queued in between. And `Thread::exec()` loops on its own `mExiting` flag without reading what
`processEvents()` returned, so on a running loop the entire effect of `WM_QUIT` is one idle pass.

The comment now says that, and cites the two tests that hold it. **The behaviour is unchanged**: not
quitting the application here is a deliberate divergence from Qt, which does quit (verified in the
local Qt 5.15.19 source, `qeventdispatcher_win.cpp`). Whether a worker's queue seeing `WM_QUIT`
should end the process is a design question, and not this pass's to answer.

## A test that hung instead of failing

Worth recording because it was caught by the mutation runs rather than by review, and because the
project already learned it once, in R31.

With `interrupt()` removed, `WmQuitEndsTheFollowingPassAndNotTheProcess` did not fail — it hung. A
pass that wrongly returned true had already drained the queue, so the next `processEvents()` blocked
in `MsgWaitForMultipleObjectsEx` with no deadline and nothing scheduled. The two checks guarding
that final call are now `ASSERT` rather than `EXPECT`, so a broken build stops there and says which
expectation broke, in 2 ms.

The same concern shaped the watchdog the other tests share: it cancels itself in its destructor and
sleeps in short slices, so a passing test pays nothing for it, a hung one fails with a reason, and a
watchdog cannot outlive its test and quit the *next* test's application. Three of the six tests ran
in 5 s each before that; the file now runs in under a second.

## Left open

- The `mMessageWindow == nullptr` fallbacks are still uncovered. Reaching them needs a test seam in
  the class — a test-only constructor flag or a virtual window-creation hook — which is production
  code reshaped for testability and a decision rather than an oversight.
- `external/QtMimic` has a byte-identical dispatcher and no equivalent tests. Its build was fixed
  here; its tests were not ported, because R22 as filed names `src/`.
- Only `win64-msvc` debug was exercised. Release and `win32-msvc` are untried.
- No Windows coverage figure. MSVC has no `-fprofile-instr-generate`, so `COVERAGE-20260814.md`'s
  caveat 1 survives as a measurement gap rather than a testing one.
